Light simulation

1.00×
12%
Every pixel is a lit 5050 package at its KiCad centre. Its light on a diffusing surface follows the cos⁴ screen law, E ∝ d²/(d²+ρ²)²: energy per pixel is conserved, the peak falls as 1/d², the tails are long. The opal (3 mm double-frosted PMMA) behaves like a screen ~56 mm above the LEDs at ~50 % transmission; the dome is clear cast PMMA (91 % LT at 3 mm, SGS) with a sanded outer face, so it is a screen at 66–266 mm whose blur comes from geometry, not haze. Bloom is applied to the whole frame. Exposure scales only what you see — the diffusers really do cost about half the light — and never touches the wire bytes.

Protocol

Binary WebSocket messages, either a raw 2417 × 4 RGBW byte frame (the exact DDP payload, offset = 4·i), or DDP packets as-is (10-byte header: flags, seq, type, id, offset u32, length u16 — the push flag 0x01 commits the frame). So the ESP32-GATEWAY can fan the same UDP packets it sends to the E4-S out over its web server, and this view shows what the sun is showing.
Sockets are blocked in the hosted copy of this page. Open the downloaded sun-simulator.html from disk, or serve it from the ESP32's web server, and live input works.

Firmware port

sun_map.h in the kit carries the same arrays this page uses (x, y, r, θ, board, run, run-index, zone) in int16 mm×10, plus sun_universe(i) / sun_channel(i). Every pattern here is written against i, x, y, r, θ, t with only sin/cos/pow and a value-noise hash, so it moves to C++ line for line.
