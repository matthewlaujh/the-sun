## 2. Physical layout — what the numbers mean

- **Disc Ø1773 mm**, pixels on concentric **rings at 30 mm pitch** (ring 0 = the single centre pixel, ring 28 = rim at r 840). 29 rings; `RING_N[ring]` = 1, 6, 12, 18 … 168 px.
- **25 boards, 3 designs:**
  - **A** — centre disc Ø448, **173 px**, centre pixel first, then a mirrored serpentine spiralling outward.
  - **B** — inner wedge, r 226→674, 30°, **109 px** ×12 (B1…B12), inner row first, serpentine row to row.
  - **C** — outer wedge, r 676→854, 30°, **78 px** ×12 (C1…C12), inner row first, serpentine. Outer row = rim.
  - 173 + 12×109 + 12×78 = **2,417**. (Older design docs say 172 for A — ignore; 173 is what's built.)
- **Sector/wedge numbering:** clockwise from the top as seen from the **LED side**; sector k spans 30(k−1)…30k degrees clockwise from 12 o'clock. Sector 1 = 12→1 o'clock. **East = sectors 1–6 (right half), West = 7–12.** Bk and Ck are in sector k.
- **Coordinate frame (used everywhere — map, JS, C):** mm, origin at disc centre, **x right, y up**, as seen facing the LED side.
- **Angle `th`:** **degrees, anticlockwise from +x** (standard math angle). So sector 1 (top-right, clockwise from 12) is `th` ∈ (60°, 90°]; sector k covers math angle `90−30k … 120−30k`. Don't confuse the *sector* convention (clockwise from top) with the *angle field* (CCW from +x).
- Rim radius `SUN_RIM_R_MM = 886.5` (used to normalise r in patterns: `rr = R/RIM`). Outermost pixel r = 840 (map says boards go to 854 incl. board edge).
- The rig is wired from the back, so when you look at the back everything is mirrored. Patterns are always written in the LED-side frame; the rig-test page has a "face-down (bench)" mirror toggle for bench work only.

### Optics — read before designing anything
Two layers above the pixels: a **3 mm opal diffuser** 14.6 mm above the PCB, then an **8 mm cast-acrylic half-dome** (outer face sanded) rising from ~8 mm above the opal at the rim to ~208 mm at the centre.

- **Resolution gradient.** Rim ≈ pixel-crisp (~72 mm blur); centre is a smooth glow (~280 mm blur). The firmware encodes this as `CORE_R = 17`: rings < 17 (r ≤ 480 mm) read as blended glow, rings ≥ 23 (the C boards) show individual pixels. **Put detail at the rim, gestures at the centre.**
- `DEPTH(r) = 8 + 200·max(0, cos(π·min(r,700)/1400))^1.5` (dome height above opal, mm); `FEAT(r) = 30 + 1.8·DEPTH(r)` = smallest feature that survives at radius r. Both exist as helpers in JS and C.
- Per-pixel colour alternation reads as grey; colour separation needs features ≳ 100 mm even at the rim and mixes to pastel by mid-radius.
- The dome's sloped band (r ≈ 450–800) catches light obliquely and reads as a lit *form* — the production show exploits this with per-ring shading and a W-channel "relief" (§5.4).
- **Design in the simulator with "dome + opal" on.**

## 3. Pixel map — `simulator/sun-map.json`

```json
{ "meta": { … run table, conventions … },
  "pixels": [ { "i":0, "run":1, "ri":0, "uni":1, "ch":1, "board":"A", "bi":0, "x":0.0, "y":0.0, "r":0.0, "th":0.0 }, … 2417 entries ] }
```
CSV has the same columns in the same order: `i,run,ri,uni,ch,board,bi,x,y,r,th`.

| field | meaning |
|---|---|
| `i` | global index 0–2416 = **output/wire order** (runs concatenated 1→8). This is the only ordering the firmware uses. |
| `run` | PixLite run 1–8 |
| `ri` | index within the run (0-based) |
| `uni` | Art-Net universe, 1-based (`meta.runs[run].universes[ri // 128]`) |
| `ch` | start DMX channel within the universe, 1-based (`1 + 4·(ri % 128)`); RGBW = 4 consecutive channels |
| `board` | `A`, `B1`…`B12`, `C1`…`C12` |
| `bi` | index within the board (LED1 = 0) |
| `x`, `y` | mm, LED-side frame, y-up — KiCad pad centres, i.e. true geometry |
| `r` | mm = hypot(x,y) |
| `th` | **degrees, anticlockwise from +x** |

Facts you can rely on:
- Index order == wire order == Art-Net order. **No remapping anywhere in software**; the ESP builds packet `uni` from bytes `4·i`.
- `i=0` is the centre pixel (there **is** one at (0,0)). Board A spirals outward from it (verified on hardware with a chase).
- Within B/C boards the order is a serpentine over rows — never assume monotonic `th` or `r` inside a board; always use `x,y,r,th`.
- Runs 6–8 chain the C boards in **descending** sector order (C5→C2, C9→C6, C12→C10). Already baked into the map. Don't "fix" it.

### `sun_map.h` (generated; identical copy in every firmware `src/`)
```c

#define SUN_PX_PER_UNIVERSE 128
#define SUN_BRIGHTNESS_CAP 0.90f  // power budget — keep
#define SUN_GAMMA 2.2f            // informational: gamma is applied by the PixLite, not the ESP
#define SUN_RIM_R_MM 886.5f

static const int16_t  SUN_X10[SUN_N], SUN_Y10[SUN_N];   // mm × 10

static const uint8_t  SUN_BOARD[SUN_N];                 // 0 = A, 1..12 = B1..B12, 13..24 = C1..C12
```

## 4. Data path and the controller contract

```
                 ┌─ sun_show:        no radio; boots and plays. USB only.
laptop/phone ────┤
  Wi-Fi AP       └─ gateway_rig_test: AP "SUN-DISC" (pw sunshine26) → http://192.168.4.1, OTA :3232 (pw sunshine26-ota)
                                   │
                        ESP32-GATEWAY (Olimex, LAN8720)  eth 10.10.0.10/24
                                   │  Art-Net UDP :6454 unicast, 23 ArtDmx packets/frame, 40 fps, output task on core 1
                                   ▼  direct Cat5, no switch
                        PixLite E4-S Mk3   10.10.0.50 static   (Expanded mode)
                                   ▼
                        8 runs → 25 boards, SK6812 RGBW
```

**Contract (both firmwares):**
- Art-Net, unicast to `PIXLITE_IP`. `ARTNET_UNI0 = 1` maps plan-universe 1 → Art-Net universe 1 (PixLite start universe is also 1; leave both).
- 1-based universes, 23 used, **128 RGBW px per universe** (512 ch). "Split pixels across universes" ON in the PixLite, so a 327-px run = 128+128+71 across 3 consecutive universes.
- **GRBW on the wire** — confirmed with Matthew; the PixLite is set to GRBW and the ESP packs `G,R,B,W`.
- **Linear values out.** The PixLite applies gamma 2.2 + temporal dithering. **No gamma in the ESP.** (The simulator applies γ2.2 itself for display, so very dim values < ~0.06 can look black there but are fine on the rig.)
- **Power.** `SUN_BRIGHTNESS_CAP 0.90` exists because full white everywhere = 967 W against PSUs at ~94 %. **There are no fuses in the rig** — the PSU overload trip is the only protection. `gateway_rig_test` always applies the 0.90 cap. `sun_show` runs `POWER_CAP 1.00` **only** because its red/orange palette + `W_MAX 90` + dark outer rings keep the whole dome ≈ 220 W peak; the README says to put 0.90 back for any white-heavy palette or flat ring curve. **Any new scene set must be power-checked before the cap is lowered.**
- Rendering must never block the network task. Output task on core 1; a render helper takes an adaptive share of each frame on core 0 (`-DSINGLE_CORE_RENDER` disables it; heavy scenes drop to ~18 fps).
- PSU zones for the load estimate: **D** = A + controllers (RSP-200-5), **E** = sectors 1–6 (RSP-500-5), **W** = sectors 7–12 (RSP-500-5). ~0.40 W/px at full white.

### 4.1 PixLite E4-S Mk3 — exact settings and how to get at it

The PixLite is configured and should not need touching. If you ever have to re-enter it (factory reset, replacement unit), this is the whole config.

**Connecting to it**
1. Power the rig (the PixLite runs off the 5 V LED PSU — no PoE).
2. Unplug the Ethernet from the ESP32-GATEWAY and plug the Mac in directly (USB-Ethernet adapter). Set the Mac's adapter to **manual IP 10.10.0.20 / 255.255.255.0**, no gateway needed. Leave Wi-Fi on; the 10.10.0.x subnet was chosen precisely so it doesn't clash with home/office Wi-Fi (192.168.0.x did).
3. Open **Advatek Assistant 3** (macOS). The E4-S appears in the device list; double-click to open its config. If it doesn't appear, the unit may be on a different subnet — Assistant can still find it by broadcast; use its "Network" tab to set the static IP below.
4. Plug the cable back into the ESP afterwards. No switch in between ESP and PixLite, ever.

**Network tab**
- Static IP **10.10.0.50**, mask 255.255.255.0, gateway 10.10.0.1, **DHCP off**.

**Pixel Outputs tab**
- Pixel type **SK6812** · colour order **RGBW** in the type, **GRBW** on every output's "colour order on wire" (this is what makes the ESP send G,R,B,W).
- **Expanded mode ON** (8 data-only runs from 4 physical outputs; CLK terminal = odd run, DATA terminal = even run).
- **Hold Last Frame ON** (the rig keeps its last picture if Art-Net stops, e.g. during OTA).
- **Gamma ON, 2.2 on all channels**, **Dithering ON**. (It was 2.0 at first light; raised to 2.2 to match the simulator.) Because the PixLite does gamma at >8-bit with temporal dither, the ESP sends linear values and very dim levels survive instead of zeroing out.
- Null pixels 0, zigzag 0, reverse OFF on every output.

**Pixel Data tab**
- Protocol **Art-Net** (DDP is implemented in the firmware too but not configured here).
- **Split pixels across universes ON** · 128 RGBW px per universe (512 ch) · **Auto Patch OFF** · universes **1-based** · every output **start channel 1**.
- Output patch (pixel count / start universe): **1: 282 / uni 1 · 2: 327 / 4 · 3: 327 / 7 · 4: 327 / 10 · 5: 296 / 13 · 6: 312 / 16 · 7: 312 / 19 · 8: 234 / 22** → 2,417 px on 23 universes. This matches `meta.runs` in `sun-map.json` and `SUN_RUN_UNI0[]` exactly.

**Things that bit us**
- **Expanded-mode terminal mapping cost an hour at first light:** the disc wired to Output 1 **DATA** stayed dark because that's run 2. Odd runs are on the **CLK** screw terminal.
- The ESP's "Art-Net universe of plan universe 1" setting and the PixLite's start universe must both be 1. Leave both.
- The PixLite has no fuses and neither does the rig; its only protection is the PSU overload trip. Don't test full-white fields at 100 % master.
- Advatek Assistant's built-in test patterns are handy for proving wiring without the ESP (select an output → test → chase). Pixel order on the rig should match `sun-map.csv` (A spirals out from the centre; B/C serpentine from the inner row).

## 5. The animation engine

Two implementations of the same engine, kept numerically matched:

1. **JS** — `simulator/source/template.html`, the `PATTERNS` array (92 patterns). Where patterns are *designed*, in the browser with the optics modelled.
2. **C++** — `scenes.h` (namespace `sc`). Line-for-line ports. `sun_show/src/scenes.h` has 17 scenes (10 ported simulator patterns + 5 "Pixel rim" scenes written straight in C + 2 shaders); `gateway_rig_test/src/scenes.h` has a larger set (≈21 + 2). **The two `scenes.h` files have drifted; `sun_show`'s is the newer one.**

**Workflow:** design in JS in the simulator → port to C in `scenes.h` → check against the JS (§5.3) → add to `SHOW[]` (sun_show) or the scene list (rig_test) → flash.

### 5.1 Pattern contract — whole-frame, not per-pixel
A pattern is a function that fills the **intent buffer** `o` (N×4 RGBW, linear 0…1) for the whole frame, looping over pixels itself, using the global geometry arrays.

**JS shape (copy exactly from an existing entry):**
```js
{ id: 'solar', name: 'Solar surface', group: 'Show', p1: 'Activity', p1d: 0.55,
  desc: 'Granulation noise over a limb-darkened disc …',
  fn(o, c) {
    const t = c.t * c.speed * 0.25, act = c.p1;
    for (let i = 0; i < N; i++) {
      const rr = R[i] / RIM;
      const n1 = vnoise(X[i] / 110 + t, Y[i] / 110 - t * 0.6, t * 0.7);
      …
      set(o, i, r, g, b, w);          // floats 0..1, linear
    }
  } },
```
- Globals available inside `fn`: `N` (2417), `X[i]`, `Y[i]` (mm), `R[i]` (mm), `TH[i]` (**degrees** CCW from +x), `RIM` (886.5), `set(o,i,r,g,b,w)`, `vnoise(x,y,z)` (value noise 0..1, 32-bit hash — uses `Math.imul`), `hash1/hash3`, `clamp01`, `fract`, `smooth`, `DEPTH(r)`, `FEAT(r)`, `skyAt(tod,horizon)` / `dayBright(tod)` for circadian patterns.
- `c` = `{ t, dt, speed, p1, P, tint:[r,g,b] }`. `c.t` is seconds (real elapsed, not frame count); multiply by `c.speed` yourself — every pattern does `c.t * c.speed * <own rate>`.
- Params: simple patterns declare one slider via `p1: 'Label', p1d: default` (value in `c.p1`, 0..1). Richer patterns declare `params: [{ k, n, min, max, step, d }, …]` and read `c.P.k`. Load-time code auto-wraps `p1` into `params`. **Only `p1` is ported to C** — extra params get baked in as constants.
- `noPal: true` = the pattern writes final colours; the palette stage is skipped (shaders, circadian sky). `group` must be one of `'Circadian sky' | 'Natural sun' | 'Rim ↔ dome' | 'Dome studies' | 'Show' | 'First light'` (the UI builds optgroups from this list).
- `scale` control: the engine swaps `X,Y,R` for scaled copies around the `fn` call — patterns never scale themselves.

**C shape (`scenes.h`):**
```c
struct Ctx { float t, speed, p1; float tint[3]; };
typedef uint16_t ib_t;                                     // intent is 16-bit fixed point (0..1 → 0..65535), 19 kB for 2417 px
static inline void set(ib_t *o, int i, float r, float g, float b, float w);
static inline void E(ib_t *o, int i, float v);             // "sun energy" shorthand = set(o,i,v, .6v, .2v, .4v)

static void p_solar(ib_t *o, const Ctx &c, int i0, int i1) {    // renders pixels [i0, i1) only
  const float t = c.t * c.speed * 0.25f, act = c.p1;
  for (int i = i0; i < i1; i++) { … X(i) Y(i) R(i) TH(i) … set(o, i, r, g, b, w); }
}

struct Scene { const char *name, *group, *p1name; float p1d; bool noPal; Fn fn; };
static const Scene SCENES[] = { {"Solar surface", "Show", "Activity", 0.55f, false, p_solar}, … };
```
- `[i0, i1)` because two tasks (one per core) render disjoint halves of the same frame. **Per-frame scalars must be recomputed inside `fn` from `c.t` only** — no static state that depends on which half you're rendering, no `static` accumulators.
- Use `float`/`<cmath>` (`sinf`, `powf`, `expf`, `fmodf`); `TH(i)` is degrees — convert to radians like the JS does.
- No heap allocation per frame. Scene tables (LUTs, neighbour lists) go in flash (`static const`) or are `malloc`'d once at boot; the static-DRAM cap is ~124 kB (`.dram0.bss will not fit` is the error).
- Cost: 2,417 px × 40 fps. Noise-heavy scenes land at ~20–60 ms/frame on the ESP; budget is 25 ms. `sun_show` prints fps to serial once a minute.

### 5.2 Post-processing chain
**Simulator / gateway_rig_test:**
```
pattern intent → [sunify: energy → palette ramp, contrast, warmth]  (skipped if noPal or palette −1)
              → tint → master × 0.90 cap → 8-bit linear → (sim only: γ2.2 for display)
```
- **sunify** = `e = clamp01(0.3R + 0.5G + 0.2B + 0.9W)`, `p = e^(0.85·contrast)`, look up a 256-entry LUT of the palette stops `[pos, r, g, b, w]`, then **warmth** shifts the ramp (− = redder, trims G/B/W; + = whiter). So most sun patterns only need to produce an **energy field** via `E(o,i,v)`; the palette colours it.
- 16 palettes in both JS and C (`PALETTES[]` in scenes.h, verbatim from the simulator): Sun (default), Sky day, Melanopic, Dawn, Golden hour, Dusk, Blue hour, Night amber, Overcast, …. Palette −1 = pattern's own colours.
- The W die is warm-neutral: "cool white" = W + B; sky-blue needs B + W (hence `noPal` on sky patterns).

**sun_show (production) adds a longer chain — all in `main.cpp`, every knob in the SETTINGS block and documented in its README:**
```
scene energy
 → × SHADE[ring]/100      per-ring gain (29 rings; tuned on the rig: 200 in the core rings 0–16, tapering 164…28 through outer B, ~6–15 on the C rings)
 → breakthrough           pixels whose raw energy > BREAK_LO are lifted toward BREAK_GAIN so rays/filaments punch through dark rings (never dims)
 → × core focus           full inside FOCUS_CORE_MM (240), easing to FOCUS_RIM (0.30) at the rim
 → × SHOW[].level→rimLevel per-scene gain, core → rim
 → soft shoulder          e' = 1 − exp(−SHOULDER·e)   (1.3) — hot clusters shade red→orange→white instead of clipping
 → SUN_SAT palette        7 stops red→orange→amber→yellow, equal-power (R+G+B+W ∝ POWER_PEAK·e^POWER_GAMMA), CONTRAST 0.95, WARMTH −0.10
 → relief                 scene energy as a height map; per-pixel slope (6-nearest-neighbour LSQ gradient from relief_nb.h) lit by a light circling once per RELIEF_LIGHT_SEC; lit slopes get +G and up to RELIEF_W of W, away slopes darken by RELIEF_SHADOW
 → MASTER_PCT × POWER_CAP → W_PER_G (W ≤ 0.75·G: no pink; pure red gets no white) → W_MAX (90) → 23 Art-Net packets, 40 fps
```
Scene scheduling: `SHOW[]` = `{ name, speedMin, speedMax, p1Min, p1Max, level, rimLevel, pace }`; currently Solar surface + Neon fluid. Each scene plays `SCENE_MIN_SEC…MAX` (30 s) then an `FADE_SECONDS` (8 s) crossfade; speed and p1 wander to a new random target every `WANDER_MIN_S…MAX_S` (5–10 s) with a 3 s ease; speed is integrated into phase so a change never jumps the picture; `pace` calibrates each scene's clock so speed 1.0 looks equally fast. Random scene at power-up. Task watchdog 12 s on the output task → reboot and restart.

### 5.3 Porting JS → C and checking it
1. Copy the body into `scenes.h` as `p_<id>(ib_t*, const Ctx&, int i0, int i1)`; translate `Math.*` → `<cmath>` floats; keep every constant; `TH[i]*Math.PI/180` → `TH(i)*PI_/180`.
2. Add a `SCENES[]` row (name, group, p1 label, p1 default, noPal, fn). In `sun_show`, scenes are referenced **by name** from `SHOW[]`.
3. Verify against the JS: the noise hash is exact-int32 in C and uses `Math.imul` in JS; verified 2026-09-30 that every ported pattern matches to < 0.02 per channel, and non-noise patterns match bit-for-bit. If you add a pattern, compare a frame from Node (load `template.html`'s PATTERNS via the `window.__sun` test hook or by extracting the array) with a native build of `scenes.h` at the same `t`. 4. Time it: serial fps line in `sun_show`, or the header fps + render-ms on the rig-test page.

## 5A. Dome shading — what it is and how to tune it

"Dome shading" is a **per-ring brightness curve** multiplied into every frame before the palette. It exists because the optics make the rig non-uniform: the centre is a deep, blurred glow under 200 mm of dome, the C boards at the rim sit 8 mm under it and show every pixel. Left flat, the same scene looks like a hot centre with a crisp speckled halo. The curve lets you decide where the sun "lives" — the look in the video is a white-hot core with the outer rings almost dark, so the rim pixels only show when a feature punches through.

**Where the curve lives**
- Tuned live on the **gateway_rig_test** page (Dome shading panel): 29 sliders in effect — the outer 12 rings (17–28, 510–840 mm) each have their own slider, rings 0–16 (0–480 mm, the diffused core) share one. Range 0–2.00 (= 0–200 %). While you drag a slider that ring lights **magenta** on the rig so you can see which ring you're on (toggle). Auto-saved to NVS 1.5 s after the last change (`sunrig/shr`). **Export config** downloads it as JSON.
- Baked into **sun_show** as `SHADE[29]` (×100 integers) in `main.cpp`. `SHADE_USE_SAVED 1` makes sun_show read the NVS curve the rig-test build saved instead (handy: tune with rig_test, flash sun_show, no retyping).
- Rings are derived from `r` at 30 mm pitch: ring 0 = centre pixel, 1–8 = board A, 9–16 = inner B, 17–22 = outer B, 23–28 = the C boards.

**The tuned curve (sun_show default, from the video):**
```
rings  0–16 (0–480 mm, A + inner B):  200 200 … 200   core saturates white-hot
rings 17–22 (510–660 mm, outer B):    164 141 112 85 54 28   smooth taper
rings 23–28 (690–840 mm, C):            6  15   6 14  6 15   near dark, faint alternation
```
The faint 6/15 alternation on the C rings was deliberate: a perfectly flat near-black rim reads as "off"; a whisper of alternate rings keeps the edge legible as rings of dots without lighting them.

**How to tune a new curve (recipe)**
1. Flash `gateway_rig_test`, join SUN-DISC, open http://192.168.4.1, Scene mode, pick the scene you'll ship, master ≈ 60–100 %.
2. Stand where the audience stands (the dome looks completely different from 1 m and from 5 m; the rim pixels disappear into the glow from a distance).
3. Set all rings to 1.00 first; then shape: push the core (shared slider) up to 2.00 if you want saturation, pull the C rings down to 0.05–0.15, then taper rings 17–22 so there's no visible step at the B/C boundary (660/690 mm). The step is the thing you'll notice most — the taper must be monotonic.
4. Watch the PSU load pills in the header. Core at 2.00 with a white-heavy palette will push E/W red.
5. Export config → paste the `SHADE[]` line into `sun_show/src/main.cpp` (or set `SHADE_USE_SAVED 1`).

**The sun_show stages that interact with the curve** (all in `main.cpp` SETTINGS, see §5.2): `BREAKTHROUGH` lets bright features ignore the dark rings (so rays reach the rim), `FOCUS_CORE_MM / FOCUS_RIM` is a smooth radial envelope on top of the stepped curve, `SHOULDER` stops the ×2.00 core from clipping flat, and `RELIEF` uses the W die to paint lit/shadow slopes over the result. Tune the ring curve first with those off (`BREAKTHROUGH 0`, `FOCUS_RIM 1.0`, `RELIEF 0`), then turn them back on.

## 5B. Experiment log — what was tried, what stuck, what didn't

Chronological, so the next person doesn't re-run the dead ends. Dates are commit dates.

**Simulator / optics (Sep 2026)**
- Built a physical optics model into the simulator rather than guessing: opal as a Lambertian emitter, the sanded dome face as a rear-projection screen at height `d(r)`, each pixel's footprint a **cos⁴ law** (FWHM ≈ 1.29·d). Opal spread modelled as an equivalent height `D_OPAL = 56 mm` (→ 72 mm FWHM at the sheet); transmission guesses `T_OPAL 0.50`, `T_DOME 0.86`. Dome material: Xintao cast acrylic, 91 % LT at 3 mm (SGS report), so bulk haze is negligible and all the diffusion is geometric. **Still unmeasured on the real rig** — the three checks (opal spread, centre FWHM ≈ 280 mm, rim colour separation) are open.
- **Per-pixel colour alternation (R/G/B checkerboard) tried for the "Additive mixing" study and abandoned** — through the opal it reads grey everywhere, even at the rim. Colour needs ≥ ~100 mm features. Observation kept in the pattern description.
- Wrote 21 "Dome studies" and 20 "Rim ↔ dome" patterns specifically to exploit the three optical facts (resolution gradient, colour mixing, the lit wall at r 450–800). Then 20 natural-sun patterns and 20 circadian-sky ones (after BIOS SkyView). 92 total. Most of these have never run on the rig; only ~10 have been ported.
- Sun palette (energy → ramp) adopted as the default so patterns only need to produce an energy field.
- Presets: Firestore (v6) → self-hosted Node/SQLite API + Caddy (v8) → plus `#preset=` links. GitHub Actions deploy was added then **removed** in favour of a manual `deploy.sh`. Server verified locally, never deployed.

**Firmware bring-up (24 Sep – 1 Oct)**
- Controller choice: UNO R4 + Ethernet shield and Nano ESP32 + shield were considered and rejected; Olimex ESP32-GATEWAY chosen for built-in Ethernet. A Portenta on an earlier project had the web server stall the LED output — hence the hard rule that the two run on separate cores.
- Subnet moved 192.168.0.x → **10.10.0.x** because the Mac's home Wi-Fi clashed while configuring the PixLite.
- First light on the disc: pixel order verified against the map by a chase. PixLite gamma raised 2.0 → 2.2 and the ESP switched to **linear output** because 8-bit gamma on the ESP zeroed everything below ~0.06.
- Map fixes at the source, not in firmware: sectors renumbered clockwise-from-top (a plain x-mirror was tried and rejected — it broke intra-board geometry; each board's block was rotated instead), then the C-boards chained in descending order to shorten the C→C hops (`pre-cw.*`, `pre-Cflip.*` kept as originals).
- The 16-bit → byte conversion wrapped full-scale 65535 to 0 (`(v+128)>>8`) — fixed to `v>>8`. Watch for this if you touch the intent buffer.
- **The blank-page / dead-OTA saga (1 Oct, ~15 commits in a day):** heavy scenes starved `loop()` so the page and OTA died; fixed by moving housekeeping to core 0 and giving the output task a guaranteed ≥5 ms sleep per frame. Then the two-core render raced; then the page went blank because the ESPAsyncWebServer + 2,417-px buffers exhausted heap — fixed by copying only the hot map tables to RAM (~29 kB), a 16-bit intent buffer (19 kB), gzipping the page (21 → 6 kB), allocating buffers *after* the network is up, and a crash-loop safe mode. Several reverts to a known-good commit (`c018073`) and a bisection build before the "Pixel rim" scenes went back in with watchdogs. Lesson: **on this board, heap and the shared flash cache are the scarce resources, not CPU.**
- The page was then **stripped** to Off/Solid/Scene + dome tuner per Matthew's direction — the per-pixel selection, channel testers and live mirror are in git history ≤ `b82bf2d` and in `gateway_disc_test`.

**sun_show — the look (2 Oct, in order)**
1. Standalone build, OTA initially kept → then **USB only** (no radio at all) to remove every network failure mode.
2. Full brightness (`POWER_CAP 1.00`) made safe by the palette: hot/dark ring curve + `W_MAX` ceiling → whole dome ≈ 220 W peak.
3. Tuned ring curve from the rig-test page becomes the default.
4. **Core focus** envelope (full inside 240 mm → 0.30 at rim) on top of the ring curve. `TEST_MODE` added.
5. **Breakthrough** — bright features (> 0.60 raw energy) lift through the dark rings so rays reach the edge.
6. Solar-surface flares changed from blocks to **tapered radial streaks** with a soft shoulder instead of a clamp.
7. Palette went **warmer** — orange/amber/yellow hot end, W ceiling 90, because on camera the W die blew out cold white.
8. **Equal-power palette** — R+G+B+W rescaled per stop to depend only on energy, so yellows aren't brighter than reds.
9. Neon fluid: edges darkened again (its raw energy is ~4× lower, lifted ×3.6 in the core only).
10. Fast timing: 30 s scenes, 8 s crossfade, 5–10 s wander (was 300–600 s / 20–60 s — too slow for a transition space).
11. One **shared speed** across scenes with a per-scene `pace` so speed 1.0 looks equally fast everywhere (Neon fluid pace 0.45).
12. **Relief** — the W die paints 3D shading from the energy height map with a light circling once a minute; neighbour table moved to flash after an OOM.
13. **No pink** — `W_PER_G 0.75`: W only where there's green, so reds stay red.

**Rejected / parked ideas**
- Browser `/update` OTA page (rejected; PlatformIO espota over the AP instead — then dropped entirely in sun_show).

- Multi-param scenes on the ESP (only `p1` is exposed; the rest are baked).

### 6.1 Setting up ESP32 OTA from scratch (gateway_rig_test)

OTA only exists in `gateway_rig_test` (and `gateway_disc_test`). `sun_show` has no radio. The ESP is its **own Wi-Fi access point**; nothing on the rig is ever on another network, so OTA is laptop → SUN-DISC → 192.168.4.1 and works with no internet at all.

**What's in the firmware (already written, `src/main.cpp`):**
```c
static const char *AP_SSID  = "SUN-DISC";
static const char *AP_PASS  = "sunshine26";      // ≥ 8 chars
static const char *OTA_PASS = "sunshine26-ota";  // must match --auth in platformio.ini
…
WiFi.softAP(AP_SSID, AP_PASS, AP_CHANNEL, 0, 4);            // max 4 clients
WiFi.softAPConfig(192.168.4.1, 192.168.4.1, 255.255.255.0);
MDNS.begin("sun");                                          // http://sun.local also works on macOS
ArduinoOTA.setPort(3232); setHostname("sun-gateway"); setPassword(OTA_PASS); setMdnsEnabled(false);
ArduinoOTA.onStart: master → 0, wait 3 frames (one black frame reaches the PixLite, which holds it), vTaskSuspend(outTask)
ArduinoOTA.onError: restore master, vTaskResume(outTask)   // a failed upload leaves the old firmware running
ArduinoOTA.handle() is called from the housekeeping task on core 0, never from the output task
```
`board_build.partitions = min_spiffs.csv` gives two 1.9 MB app slots on the 4 MB flash; the bootloader swaps slots after a successful upload, so a bad image can't brick it — a failed or interrupted OTA boots the previous slot.

**`platformio.ini` (two environments, same code):**
```ini
[env:usb]
upload_speed = 460800          ; CH340 is flaky at 921600; hold BUT1 during "Connecting…" if auto-reset fails

[env:ota]
upload_protocol = espota
upload_port = 192.168.4.1      ; the ESP's own AP address
upload_flags =
  --port=3232
  --auth=sunshine26-ota        ; = OTA_PASS
```

**One-time setup on a new laptop (needs internet — do it before you're anywhere near the rig):**
1. Install PlatformIO Core ≥ 6.2 (`pip install platformio` or the VS Code extension; `pio upgrade` if older — the pioarduino "stable" platform refuses older cores).
2. `cd firmware/gateway_rig_test && pio run -e usb -e ota` — compiles **both** environments so every package and both `.pio/libdeps/<env>/` caches are populated. Building only `usb` leaves `ota` trying to download on first use, which fails on SUN-DISC.
3. Dry-run with Wi-Fi off: `pio run -e ota` must build with no network. If it tries to fetch anything, repeat step 2.
4. Never `pio pkg update` / `pio upgrade` / change `platform =` right before a rig session.

**First flash (USB, once per board):**
```
pio run -e usb -t upload     # micro-USB on the GATEWAY; hold BUT1 while it says Connecting… if needed
pio device monitor           # 115200 — you should see: [sun] AP "SUN-DISC" / "sunshine26" → http://192.168.4.1 · OTA :3232 · eth 10.10.0.10 → 10.10.0.50 uni 1
```

**Every flash after that (over the air):**
1. Join the laptop to Wi-Fi **SUN-DISC** (password `sunshine26`). You will have no internet while joined.
2. Optional: open http://192.168.4.1 and note the **build pill** in the header (compile date/time + light|dark).
3. `pio run -e ota -t upload`. espota authenticates, the rig goes black for the upload (~20–40 s), the ESP reboots into the new slot, the AP comes back within ~5 s.
4. Reload the page: the build pill should show the new time. Flipping `-DUI_DARK=1` is the quick visual proof an upload actually landed.
5. macOS will ask once to allow "Python" to accept incoming connections — **allow it**, or espota hangs at "Waiting for device".

**If OTA fails:**
- "No response from device" / "Waiting for device": laptop not on SUN-DISC, or the firewall prompt was declined (System Settings → Network → Firewall → allow Python), or the ESP is mid-crash-loop (serial shows the reset reason; USB-flash to recover).
- "Authentication failed": `--auth` in `platformio.ini` ≠ `OTA_PASS` in `main.cpp`.
- Upload starts then dies: heap pressure on the ESP. Wait for the page's heap figure to be > 60 kB (don't have the page open and polling while uploading), or set master to 0 first.
- Rig stays black after a failed OTA: `onError` should have resumed output; if not, power-cycle — the old slot boots.
- Changing the AP name/password or OTA password means changing both `main.cpp` and `platformio.ini`, and tells the next person: the credentials are the only key into a mounted rig.

**Adding OTA to `sun_show` (if you want it back):** the code is in `gateway_rig_test/src/main.cpp` (`otaSetup()`, the `[env:ota]` block, `AP_*`/`OTA_PASS`, `houseTask` on core 0 calling `ArduinoOTA.handle()`). It was removed from sun_show on purpose to delete every network failure mode; the suggested compromise is to start the AP only while BUT1 is held at boot (§10).

**Physical access:** once the sun is mounted the ESP32-GATEWAY is unreachable; the only ways in are the rig-test build's AP/OTA or pulling the rig. `sun_show` deliberately has no radio, so **choose which firmware is on the board before mounting**, and don't ship a sun_show build you haven't soak-tested.

**Matthew's direction (2026-10-01):** keep firmware and page barebones — scenes plus the ring-shading tuner, nothing per-pixel — and prioritise network robustness and animation performance over page features. Watchdogs/self-recovery must keep the page and OTA reachable without breaking OTA.

## 8. Conventions and gotchas

- **2,417 px, 23 universes used (`SUN_UNIVERSES` is 24 = array size), 8 runs, 25 boards, 29 rings.**
- **Index == wire == Art-Net order. No remap in software.**
- **Linear out; the PixLite does gamma. GRBW packing. 0.90 cap unless you've power-checked the scene set. No fuses.**
- **`th` is degrees, CCW from +x.** Sectors are numbered clockwise from the top. Both are correct; they're different things.
- Two superseded maps (`pre-cw`, `pre-Cflip`) live next to the real one — never load them.
- Patterns render the **whole frame** (JS) or a **half-open index range** (C). No static per-frame state in C.
- JS noise uses `Math.imul`; C uses `uint32_t` multiplies. Keep them identical or the two engines diverge visibly.
- `scenes.h` exists in two firmwares and has drifted — `sun_show`'s is current. Any palette/sunify change must go into `template.html` **and** the `scenes.h` you ship.
- `sun_map.h` and `relief_nb.h` in `src/` are generated copies — never hand-edit.
- `index_html_gz.h` is generated on every rig-test build and gitignored.
- Git: Matthew pushes. Commit locally with his identity if working on his Mac.

### Optics — getting more diffusion out of the acrylic
The current look depends on the rim being *too* sharp: the outer 12 rings are held near-dark because they show individual pixels. The alternative is to make the dome diffuse harder so the rim can be used. Options, cheapest first:

1. **Sand the inside face too.** Only the outer face is matte; the inner is polished. A second frosted surface roughly doubles the scatter and, crucially, the *inner* face is where the light enters, so it spreads before crossing the 8 mm shell. Test on an offcut: 400–600 grit random-orbit, then compare FWHM of a single pixel through single- vs double-frosted samples.
2. **Coarser / deeper outer frost.** Hand-sanding gives a fine haze that scatters at small angles. Bead-blasting (glass bead, 80–120 mesh) or 180–240 grit gives wider scatter and hides pixels better, at the cost of a few % transmission. The SGS 91 % figure is for clear stock; expect ~80 % after a heavy frost.
3. **Raise the opal off the PCB, or add a second opal.** The opal is 14.6 mm off the LEDs; its blur scales with that gap. Spacers to 25–30 mm would push the 72 mm rim blur toward ~120 mm, enough to merge adjacent pixels at the rim. If there's no room, a second thin (2 mm) opal or a sheet of diffusion film (Lee 216 / Rosco 3026 or a 3M/Brightview-style volumetric diffuser) between the opal and the dome does the same.
4. **Volumetric diffuser instead of surface frost.** A satin/"frosted-through" cast acrylic (e.g. Evonik Satinice-type or any "LED diffuser sheet" with ~50–70 % transmission and 90 %+ haze) scatters in the bulk rather than at one surface, so the result is independent of viewing angle and hides the hot spots from the sanded face. A thin thermoformed insert inside the existing dome avoids re-making the dome.
5. **Edge treatment at the rim only.** The problem is the last ~150 mm. A ring-shaped diffuser (an annulus of opal or film laid on the C boards, under the dome lip) targets exactly where the dome is thinnest, and leaves the centre alone.
6. **Light-piping is small but real.** The sanded outer face breaks TIR; if the inner face is also sanded, light piping along the shell drops further, which reduces the faint rim glow line some people will see at the dome edge.

How to decide: light one C-board pixel at the rim with the dome in place and photograph it from 3 m with a locked exposure; measure the spot's width at half-brightness. Repeat for each treatment on an offcut held over the same pixel. The target is a spot ≳ 90–100 mm (3 pixel pitches) so adjacent pixels merge; at that point the `SHADE[]` curve can be opened up on the C rings and the whole 1.77 m becomes usable.
